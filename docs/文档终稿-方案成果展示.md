## 二、方案成果展示

### 1. 命题场景描述、问题描述及痛点说明

#### 命题背景

瑞幸已经建立由 App、小程序、外卖平台、企业微信、社群、短信和 Push 组成的高频触达体系。但在 AI Agent 时代，用户可能不再主动打开这些渠道，而是直接向个人 AI 助手表达需求。品牌争夺的重点，正在从传统入口的点击率，转向 Agent 场景中的**推荐权、调用权和执行权**。

北京几乎每一栋写字楼下都有一家瑞幸，上班族日均点单是极普遍的行为——但这只是切入点，不是我们要解决的痛点。个人点单本身体验已经足够顺畅，真正的空白在"团队场景"和"钱与工作场景分离"这两件事上，而这两件事，恰好都指向同一类人：**买单的人**。

#### 用户定位：谁在买单

我们的用户不是喝咖啡的员工，是**决定买单、张罗这件事的企业老板/团队负责人**，锁定两类典型画像：

**A. 专业服务型中小机构老板**（金融、咨询、法律）
接待客户、组织临时小会是日常，咖啡消费在这类机构里接近工作刚需，不是福利点缀；决策链条短，老板自己能拍板要不要用一个新工具。

**B. AI native 创业公司/互联网公司老板**
团队重度使用 AI，飞书是默认工作平台，本身就认同"能交给 Agent 做的事就不用人做"这套逻辑——不需要教育他们为什么要在工作场景里用 AI 机器人完成一件事。这类公司通常也没有大厂式的茶水间免费咖啡机，团队咖啡这件事此前没人管。

两类老板的共同点：都不是那杯咖啡的主要饮用者，都已经把飞书当成日常工作的操作系统。

#### 四个痛点

**痛点一：团队/会议场景下的批量下单，现在是纯人肉活。**
A 类老板接待客户、组织 4-6 人小会前，要一个个打开小程序帮团队配置不同口味，或者在群里接龙、垫钱报销；B 类老板想在冲刺/庆功时"请团队喝一杯"，同样要么逐人确认口味逐人下单，要么发红包让大家自理，体验割裂，没有"老板请客"的仪式感。这条我们已经在飞书 bot 里真实做出来并跑通过真实下单：一句话在群里收集多人偏好，自动合并成一单支付。

**痛点二：钱和工作场景是分离的。**
现在的路径是员工自己垫钱、事后找老板/财务报销，或者老板转账后让员工自己去下单——"钱"这一步永远要跳出飞书这个工作场景才能完成。让 bot 常驻飞书群，意味着"提出需求→下单→支付"这个完整动作可以不离开工作场景一次性走完，费用直接挂在企业账号上。

**痛点三（战略级）：如果瑞幸不占住这个位置，会被别人的 Agent"代理"掉。**
命题原文说得很直白：品牌争夺的重点正在从渠道点击率转向 Agent 场景里的推荐权、调用权和执行权。对 B 类 AI native 团队来说，这不是假设——他们本来就在把越来越多工作交给 Agent 处理。如果瑞幸不主动在飞书这类工作场景里维护一个官方 Agent 身份，员工未来大概率会用自己的私人 AI 助手完成"点咖啡"这件事，瑞幸就从"直触用户的品牌"退化成"被别人的 Agent 调用的后台库存"，用户关系和议价权都会被稀释。这一条是对命题背景的战略推理，不是访谈证据。

**痛点四：下单是"即时"的，没有"预定"这一层，容易被日常琐事挤掉。**
我们实测验证过：瑞幸微信小程序官方商城不支持提前预定下单，只能即时购买；我们审计过开放给 Agent 的官方 MCP 工具（`previewOrder`/`createOrder`）同样全部是即时下单接口，没有一个支持"定时/周期性批量下单"。这意味着团队咖啡这件事永远要靠人当天手动发起——员工可能忙起来就忘了喝，老板想固定给团队安排"每天早上一杯""每周三下午茶"，也只能每次重新张罗。我们在 Agent 层直接补上这一层空白：由我们的 bot 用定时任务触发批量下单（比如"每天 9 点自动帮团队下单"），一次设置，长期生效——这是官方渠道现在完全没有、我们能提供的差异化能力。这既解决员工遗忘的问题，也把老板从"每次手动发起"里解放出来。

### 2. 方案优势/创新点

**核心突破点**：这个"数字员工"由商家（瑞幸）自己创建、自己拥有，不是被动等第三方 AI 平台调用。瑞幸官方已经有 MCP + CLI，能在电脑上用命令行完成下单，但 CLI 对绝大多数普通用户（尤其是老板/HR 这类非技术人员）完全不可用。我们把这个锁在开发者工具里的能力，原样搬进飞书——企业员工真正每天在用的工作界面，变成一个真正能用的数字员工。更关键的是所有权：AI 员工最核心的资产是用户交互数据、会话历史、偏好画像，这些只有在"商家自己拥有并运营这个 Agent"的架构下才留得住——不是被动等着被调用，是主动把执行入口开在企业最高频的工作场景里，自己攥住调用权。这正是对命题"推荐权、调用权、执行权"最直接的回应。

**AI 能力创新用法**：
- 双模式路由——一次轻量分类调用判断"直接下单"还是"DIY 收集"，两套系统提示词互不干扰，不用一个又长又啰嗦的提示词硬撑所有场景
- "本地伪工具"设计——DIY 收集收敛时，让模型用结构化参数（`resolveDiy`）报告结果，而不是把内部状态暴露给用户，用户只看到干净的对话
- 防幻觉护栏——开发过程中真实抓到过大模型会凭训练记忆"编"出恰好合法的商品 ID 去下单，我们加了一层代码校验：`previewOrder`/`createOrder` 里的每个商品，必须能在本次会话真实工具调用结果里追溯到，查不到就拦截，不放行

**预计可产生的量化价值估算**（估算，非实测数据）：4-6 人小会点单场景，人工逐一确认口味、逐一下单，估算单次操作 5-10 分钟，还容易漏单/记错口味；用这套方案，群里一句话收集偏好、自动合并下单，估算 1-2 分钟完成，并有防幻觉校验兜底不会下错商品。

|---|---|---|

| 钱与工作场景 | 员工垫钱→事后报销，或老板转账→员工自己下单，"钱"这一步永远要跳出飞书 | 提出需求→下单→支付全程不离开飞书，费用直接挂在企业账号 |

### 3. 具体方案说明（突出 AI 能力）

方案由两个并存的对话模式组成——**直接下单模式**（用户已经明确知道要什么）和 **DIY 饮品专家模式**（用户只有模糊灵感）——通过一次轻量意图分类实时路由，背后共享同一套瑞幸官方 MCP 工具链和防幻觉护栏。下面按评分表四个维度逐条展开，方便对照打分。

#### AI 应用创新性（对应评分点①②③）

**① 问题切入是否新颖**：多数团队会把"AI Agent 流量运营"理解成"做一个更聪明的推荐/客服机器人"，切入点停留在内容和交互层面。我们的切入点是**所有权结构**——数字员工的身份归属决定了长期谁攥着用户关系和数据。这是一个平台/生态位置问题，不是一个功能设计问题，也是我们认为唯一能回应命题里"调用权、执行权"这两个词的切入方式：不是让 Agent 用得更顺手，是让品牌自己成为那个 Agent。

**② AI 用法是否突破常规**：常规做法是给一个大模型套一份长提示词、接入几个工具，让它"尽力理解用户意图"。我们做了三处反直觉但更稳的设计：
- **不用一个提示词硬撑所有场景**，而是先用一次几乎零延迟的轻量分类（`router.js`，`max_tokens: 10`，无工具、无长上下文）判断意图，再切到对应场景的干净提示词，两套提示词互不污染
- **不让大模型自由生成最终决策**，DIY 收敛时强制走结构化工具调用（`resolveDiy`）而不是自由文本，把"用户体验的干净"和"系统拿到可用数据"这两个互相冲突的目标，用同一个机制同时满足
- **不信任大模型自己报告的下单参数**，即使它输出的 `productId`/`skuCode` 格式完全合法，也要求能在本次会话真实工具调用结果里追溯到才放行——这个设计直接来自开发过程中抓到的真实事故：模型凭训练记忆编出了一个格式正确、编号也凑巧存在的商品参数，如果没有这层校验，会真实下错商品

**③ 是否有原创性的 Agent / Prompt / 工作流设计**：DIY 饮品专家 Skill 不是简单的"多轮问答直到用户说够了"，而是设计为一个四层架构：

1. **专家知识层**：系统提示词内置一份精炼的调饮逻辑映射（口感描述 → 风味方向 → 冲调参数的对应关系，比如"清爽+不要奶感"应优先考虑果咖/茶饮基底而非奶咖基底，"浓郁+要顺滑"应优先考虑厚乳/丝绒基底），让模型的判断有一套专业调饮师会用的决策依据支撑，而不是自由发挥的联想。
2. **槽位压缩层**：把"场景/口感/风味/咖啡感/温度甜度"五个专业维度，动态压缩进最多 3 轮问答——不是机械地一步步问完固定顺序，而是根据用户已经透露的信息量实时判断哪个槽位还缺，用复合选项一次性收集多个维度（例如第一轮同时问口感方向+风味偏好），缺信息才问，够了就跳过。
3. **结构化收敛层**（`resolveDiy` 本地伪工具，已在当前 demo 中验证可行）：所有槽位填满或问满 3 轮强制收敛后，模型必须把内部判断封装成结构化参数上报，代码层据此决定下一步，用户全程只看到干净的对话，看不到"研发进度""槽位状态"这类内部术语。
4. **双出口设计**：收敛后走两条路径——能匹配现有商品的，转入真实商品验证与下单流程；匹配不到的，把同一份结构化偏好数据写入新品许愿池。这两条出口共用同一个数据 schema，意味着"服务当场这个用户"和"沉淀长期研发信号"不需要维护两份数据格式，是同一个动作的两个副产品。

当前 demo 已经验证了这套架构里最核心的机制——3 轮收敛、`resolveDiy` 结构化上报、双出口分流——真实产生过 3 条许愿池数据（含用户原话、结构化偏好、缺口原因）；专家知识层的完整调饮映射表和槽位动态判断逻辑是本方案设计的下一步细化内容，当前版本用简化提示词验证了机制可行性。

这一整套架构直接对应命题里"重构会员关系，打通唤醒、推荐、下单、复购、长效忠诚全运营闭环"这句话：口味记忆机制（`tastes.js`）让每一次下单都成为下一次对话的上下文，是"复购"环节的技术地基；DIY 收敛不到现有商品时沉淀的许愿池数据，是把单次交互转化为长期研发信号的"长效忠诚"载体——用户的个性化需求被真实记录、真实可能影响未来产品，而不是被系统遗忘。这两点让整个方案不止是一次性交易工具，而是一个能持续积累会员关系数据的运营闭环。

#### 业务价值（对应评分点①②③）

**① 对企业出题的业务痛点响应度**：一一对应第一节四个痛点——团队批量下单（已验证）、钱与工作场景分离（已验证）、Agent 时代调用权的战略应对、预定能力的空白填补。

**② 量化收益**：
- 效率——团队批量下单从估算 5-10 分钟压缩到 1-2 分钟
- 成本——第三方 AI 助手/分发平台若作为交易中间层，行业常见的抽成区间在个位数到双位数百分比不等；商家自建自有 Agent 省去这层持续性抽成，且瑞幸是高频复购品类，抽成成本会随订单量线性放大，自建的长期摊薄效应会随时间推移更明显
- 收入——飞书应用商店免费分发本身是新客户获取渠道，企业付费套餐（复用瑞幸卡预充值机制）是可叠加的增量收入线

**③ 价值可验证性**：不是纸面测算。当前 demo 已经真实产生过真实订单、真实支付二维码（瑞幸官方支付网关直接生成，非自制），也真实产生过 3 人不同口味的合并订单（总价 ¥36.9，一次支付），以及 3 条真实的许愿池数据——每一项都可复现，不是假设性描述。

#### AI 应用深度（对应评分点①②③④）

**① 是否深入到核心业务链路**：AI 直接执行"查商品→算价格→下单→生成支付二维码"这条真实交易主链路，不是停留在推荐话术或客服问答这类外围环节。

**② AI 参与是否解决关键环节而非边角**：AI 承担的是"完成一笔真实交易"这个核心动作本身，包括商品匹配、多人偏好合并、防幻觉校验、支付发起，而不是给人类操作者提供辅助建议后仍需人工完成下单。

**③ Agent / 工作流复杂度与鲁棒性**：
- 并发请求按用户排队处理，避免同一用户的多轮消息互相踩踏会话状态
- 工具调用步数设有上限兜底（10 步），超出后优雅降级为提示用户重新表达，而不是无限循环或报错崩溃
- 防幻觉校验拦截未经验证的下单参数，并将拦截原因反馈给模型，引导它重新调用真实查询工具，而不是简单报错终止
- 系统提示词工程上处理过底层模型（MiniMax-M3）的两个真实缺陷：偶发思维链内容泄漏进正式回复的兜底清洗、多轮对话中间插入 system 角色消息导致接口拒绝请求的问题（改为拼入 user 消息解决）

这些都是开发过程中真实遇到、真实修复的鲁棒性问题，不是理想状态下的假设设计。

**④ 对飞书 AI 能力的应用深度**：不只是调用了最基础的发消息接口，还组合使用了事件订阅（`im.message.receive_v1` 被动接收）、主动消息推送（下单结果、支付二维码不需要用户先发言即可主动推送）、图片消息上传与发送（支付二维码从瑞幸网关下载后转存至飞书图床再发送）、群成员信息解析（把 `open_id` 解析为真实姓名用于口味记录）。同时接入飞书妙记，将用户访谈转成结构化的智能纪要和文字记录，作为本方案痛点分析的原始依据之一。

#### 方案完整度、可落地性与可推广性（对应评分点①②③④）

**① 业务闭环是否完整**：问题发现（开发过程中真实暴露的技术缺陷）→ 方案设计 → 执行 → 验证 → 迭代，这个循环在开发过程中完整走了多轮——例如防幻觉护栏、并发排队、跨轮次商品参数记忆这几个机制，全部是先出现真实故障、再针对性修复、再验证通过的迭代产物，不是一次性设计好就没再改动过。

**② 方案链条完整度与内在一致性**：从"用户表达需求"到"完成支付"没有断点，每一步都有可复现的真实测试证据支撑，模式路由、工具调用、数据记录三层架构互相衔接，没有需要人工介入补漏洞的环节。

**③ 在出题企业内可落地的可行性**：完全基于瑞幸已经公开发布的官方 MCP 工具和飞书官方开放平台的自建应用能力搭建，没有依赖任何尚不存在或需要瑞幸额外开发的接口，理论上瑞幸内部团队可以直接在现有代码基础上继续投入。

**④ 可复制到同行业/跨行业的推广潜力**：这套"商家自建数字员工进驻企业协作工具"的模式，核心不是瑞幸和飞书专属的技术方案——同类高频消费品牌（奶茶、便当、鲜花）、其他企业协作工具生态（企业微信、钉钉）都可以复用同一套"意图路由+防幻觉护栏+结构化收敛"的工作流设计思路。

### 4. 方案价值

方案落地后，对瑞幸命题场景带来的价值可以从三个层面看：

**对终端消费场景**：团队/会议批量下单从估算 5-10 分钟的人工操作压缩到 1-2 分钟，且防幻觉护栏保证不会下错商品；预定/定时批量下单填补官方现有渠道完全空白的能力，减少"忘记喝咖啡"和"每次重新张罗"两类损耗。

**对企业客户关系**：以"商家自建数字员工"的身份主动进驻企业最高频的工作场景（飞书），意味着用户交互数据、会话历史、口味偏好这些资产留在瑞幸自己手里，不是被某个第三方 AI 助手平台截留——这是应对命题里"品牌无法直触用户"这一背景假设最直接的解法。

**对新品研发链路**：DIY 专家模式收敛不到现有商品时产生的许愿池数据（已有 3 条真实记录），把"现有菜单满足不了的真实需求缺口"沉淀成结构化数据，长期积累后可以反哺新品研发方向判断，这条价值链目前在方案里已经打通机制，尚未达到有统计意义的数据规模。
