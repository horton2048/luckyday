# Lucky Barista 飞书机器人 v2 开发规范

替代 v1 的单一五阶段 Skill 模式。v1 问题：提示词太长、回复太啰嗦、把内部状态（"研发进度 1/5"）暴露给用户、只有一种模式没法直接下单。

## 一、两个模式，一个路由

机器人不再只有"访谈"一种行为，而是先判断用户说的是哪种意图，再进对应模式。

```
用户消息
  │
  ├─ 意图分类（模型判断，不需要用户显式选模式）
  │
  ├─→ 【模式A：直接下单】用户已经知道自己要什么
  │     "帮我点一杯标准美式" "来杯生椰拿铁，冰的"
  │
  └─→ 【模式B：DIY 收集】用户在描述灵感/偏好，还没有明确商品
        "我想做一杯清爽点的咖啡" "有没有柚子味的"
```

分类逻辑：用户消息里出现明确、可识别的瑞幸商品名或高度具体的下单要素（商品名+温度/糖度等）→ 模式A；否则默认模式B。分类由同一个模型在系统提示词里用一句规则完成，不需要额外分类调用。

## 二、模式A：直接下单

**没有 Skill 式的人格化提示词**，系统提示词只有工具使用规则，类似：

```
你是瑞幸下单助手。用户说想喝什么，你负责：
1. 缺门店信息就先问门店（或用用户上次用过的门店）。
2. 用 searchProductForMcp 找到匹配商品。
3. 找到后直接报价（previewOrder），一句话展示价格，问"确认下单吗？"。
4. 用户确认后才调用 createOrder。
回复必须简短，不超过 2 句话，不要解释你在做什么。
```

- 不引导用户"讲清楚场景/口感/风味"，用户说了什么就按什么找。
- 找不到精确匹配时，最多给 2 个候选选一个，不展开分析。
- 全程一样遵守：只有用户明确确认价格后才 `createOrder`。

## 三、模式B：DIY 收集访谈

### 3.1 硬约束

| 约束 | 规则 |
|---|---|
| 轮次上限 | 最多 3 轮追问（不是 v1 的 5 阶段）。第 3 轮问完必须收敛到"推荐"或"存愿望单"，不能再问第 4 个问题。 |
| 回复长度 | 每条回复 ≤ 2 句话（不含选项列表本身）。不写背景解释、不写"我理解你想要..."这类复述。 |
| 禁止内容 | 不展示"研发进度 X/N"、不展示内部 stage 名（SCENE/TASTE/FLAVOR 等）、不输出 JSON 结构给用户看。 |
| 提问方式 | 优先给 2-4 个选项（"清爽 / 顺滑 / 浓郁，选一个或都不选"），不要开放式"你想要什么样的口感？" |

### 3.2 三轮问什么

不再是 v1 的五个独立维度各问一次，压缩成 3 轮，每轮可以合并追问多个维度：

1. **第 1 轮**：口感 + 风味方向（用选项：清爽/顺滑/浓郁/果香，选完顺带问风味方向）
2. **第 2 轮**：咖啡感 + 温度/甜度（选项：轻/平衡/浓；冰/热；正常糖/半糖/不加糖）
3. **第 3 轮**：只在信息仍不足以匹配时才问，否则跳过直接进入收敛。

如果用户在第一轮就把信息说全了（像"我想要清爽的柑橘冰美式不加糖"），直接跳到收敛，不用凑满 3 轮。

### 3.3 收敛两条路

**路 A：能匹配现有商品**
- 调用 `searchProductForMcp` 找到候选
- 一句话推荐："柚C美式挺接近，要不要试试？"
- 用户说好 → 无缝转入模式A的下单流程（同一个会话里直接继续，不用户重新描述）

**路 B：匹配不到**
- 不能编造一个"接近但不对"的商品硬推荐
- 写入愿望单（见第四节），一句话告知："这杯现在做不出来，我记下来了，攒够人一起投票就有机会上新。"

### 3.4 示例对话（体现"简短+选项"的风格）

```
用户：我想做一杯清爽点的咖啡
机器人：偏果香还是偏顺滑？
        1. 果香清亮  2. 奶香顺滑  3. 都要点

用户：果香
机器人：咖啡感要多少？
        1. 轻，主要喝果香  2. 平衡  3. 浓一点

用户：平衡，冰的不加糖
机器人：柚C美式挺接近——冰、不加糖、咖啡感平衡，¥12.9，要预览一下吗？
```

## 四、愿望单数据

v1 只在 SKILL.md 里口头描述了字段，从没真正落过数据。v2 要求：走到"路 B"必须写入一条真实记录，不是聊天说说就算。

### 4.1 存储

MVP 阶段用本地 JSON 文件（`data/wishlist.json`，追加写入），不引入数据库。字段：

```json
{
  "id": "wish_20260814_001",
  "createdAt": "2026-08-14T16:00:00+08:00",
  "feishuUserId": "ou_xxx",
  "rawUserWords": ["我想做一杯清爽点的咖啡", "果香", "平衡，冰的不加糖"],
  "collected": {
    "taste": "果香清亮",
    "coffeeIntensity": "平衡",
    "temperature": "冰",
    "sweetness": "不加糖",
    "flavor": "未知/用户没说具体是什么果"
  },
  "gapReason": "现有菜单里同时满足果香清亮+平衡咖啡感+这个甜度的商品未找到",
  "status": "待聚类"
}
```

### 4.2 后续（不在本次开发范围，只是标注方向）

- 许愿池的"聚类/投票"功能本次不做，只负责真实落数据。
- 数据量大了再迁移到数据库，MVP 阶段文件足够。

## 五、系统提示词改造方向

v1 的 `src/skillPrompt.js` 直接读一整份 SKILL.md（五阶段说明书）当系统提示词，v2 要拆成两份短提示词，模式A和模式B分别用一份，而不是共用一份长文档：

- `prompts/order.md`：模式A用，几行字，纯工具调用规则
- `prompts/diy.md`：模式B用，包含 3 轮上限、简短话术、选项化、两条收敛路径的规则

路由（判断模式A/B）本身也是一段简短提示词，或者做成一次轻量分类调用。

## 六、待确认问题（需要你拍板）

1. **路由方式**：模式判断放在同一次模型调用里（省一次请求，但提示词要同时装两套规则，可能变啰嗦），还是先用一次轻量调用专门分类、再切到对应模式的干净提示词（多一次请求，但两个提示词能保持真正精简）？
2. **模式切换后的会话**：用户在模式B收敛后转模式A下单，算同一个会话继续，还是重置成新会话？（推荐同一个会话继续，带着已收集的偏好，不用户重新说一遍）
3. **愿望单要不要在群里有反馈**：比如攒够 N 条相似愿望时要不要主动播报？（本次不做，只是确认要不要在规范里明确排除）
