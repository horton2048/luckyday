## Problem Statement

现有的 Lucky Barista 飞书 bot（本次会话前半段已实现并验证）解决的是"在飞书里完成瑞幸下单"这个技术问题。但这只是执行层，没有回答一个更根本的问题：**这个 bot 存在的理由是什么，谁会主动把它加进工作群，为什么**。本次 office hours 要回答的是产品定位、目标用户和商业模式，不是技术实现。

## Demand Evidence

**诚实记录：核心商业假设目前 0 个直接验证。**

- 会话中途提出"企业老板买单"这个洞察时，我去核实了 `用户访谈/` 目录下的原始访谈材料，发现唯一提到"老板"的地方（`02-文字记录-妙妙的用户调研-2026-08-09.md:1275`）说的是完全不同的事（关键词检测触发会议建议），跟"企业买单"无关。
- 用户确认后承认这是团队推断，不是访谈里任何人说过的话。
- 已有的、真实的证据只有一条：`用户访谈/01-2026-08-09-妙妙-深度用户访谈.md` 里明确写着"本次受访者所在部门因对外沟通较多而点单频率较高，但单一样本具有随机性，不能直接代表群体需求"——访谈者自己都标注了这是单样本、不能代表群体。

**结论：目前的产品方向建立在推断上，不是已验证需求。** 这不是否定方向，而是必须承认现在做的每一个决定都是在下注，不是在响应已知事实。

## Status Quo

企业员工/团队现在点瑞幸咖啡的方式：**各自打开瑞幸官方 App/小程序分别下单**，没有协同工具，也没有表现出"急需一个协同工具"的信号——用户自己确认了这一点。

这意味着一个关键风险：如果个人下单体验本身没有摩擦，"多杯合并下单"这个功能解决的可能是一个不存在的痛点。会话中期已经把这个疑问挑明过，用户给出的回应是：真正的差异化不在交互体验，而在"企业福利/补贴入口"——瑞幸官方 App 做不到"公司出钱、员工在工作场景里直接领取"这件事。

## Target User & Narrowest Wedge

**用户不是铁板一块，必须分两类，产品打法完全不同：**

- **A 类：已有免费茶水间咖啡机的大厂员工。** 日常咖啡需求已被内部供给满足，边际转化空间小。真正会触发下单的时刻是免费咖啡机覆盖不到的场景：临时会议/接待客户需要"拿得出手"的非咖啡品类（生椰、果茶）、加班冲刺时团队负责人一次性犒劳多人、接待访客的体面需求。
- **B 类：没有内部咖啡供给的中小企业员工。** 这类才是真正的日常高频场景，产品需要的是"每人每天一杯额度"式的福利管理机制，跟 A 类的"场景触发式"完全不同。

**当前 demo 覆盖的是最窄的楔子：** 个人（老板/HR）用自己的瑞幸账号 token，把 bot 加进自己公司的飞书群，全员可以直接 @ 机器人点单，多人多杯自动合并成一单——这个楔子已经在本次会话里跑通并验证（含真实下单、真实支付二维码）。

## Constraints

- 飞书机器人推送范围严格限定在已安装该应用的企业内部，不是公开增长渠道——分发依赖"拿下更多企业"，不是内容裂变。
- 飞书是工作场景，员工/管理员对营销骚扰容忍度极低，一旦被投诉，应用会被管理员直接移出——这条约束直接否决了"复用微信公众号式主动营销推送"的运营思路。
- **分阶段的技术要求，不要混为一谈：**
  - **验证阶段（当前，1-2 家企业）**：不需要 ISV、不需要多租户重构。每家企业各自用飞书"自建应用"（跟当前 demo 完全一样的模式）+ 各自绑定自己的瑞幸 token，物理上就是彼此独立的部署，天然隔离，不需要额外工程量。
  - **规模化阶段（飞书应用商店多企业分发）**：必须以真实公司主体走 ISV 服务商入驻流程（见 [飞书 ISV 服务商入驻文档](https://open.feishu.cn/document/isv-guides/publish-your-app/step1-complete-the-entry?lang=zh-CN)），且要把单租户 `tenant_access_token` 实现重构成按 `tenant_key` 隔离的多租户版本——这是进入规模化阶段的前置工程量，不是验证阶段的阻塞项。

## Premises

```
1. 差异化价值不是"聊天式下单体验更好"，而是"企业福利/补贴渠道"——瑞幸官方 App 做不到"公司买单、员工领取"这件事。（用户确认同意）
2. 多杯合并下单（部门/会议场景）是真实存在的使用场景，但目前 0 个具体验证。（用户确认同意，选择先不管、继续按此方向推进）
3. 目标买家是企业方（HR/团队负责人/老板），不是终端喝咖啡的员工——获客路径是 to B，不是 to C 增长。（用户确认同意）
4. 现有技术地基（Skill + MCP + Feishu bot）已经跑通"下单"这个动作本身，剩下的核心工作是分发机制和商业模式设计，不是继续打磨下单交互。（用户确认同意）
```

## Approaches Considered

### Approach A：优惠券核销壳子（最小可行）
复用已经接好的 MCP `couponCodeList` 参数，做企业发券、bot 自动核销。工作量 S，风险低，能最快出一个可演示的"企业福利"demo，但没有解决"企业愿不愿意付钱囤券"这个根本没验证的问题。

### Approach B：完整企业福利后台（理想架构）
给企业方做真正的管理后台（充值预算、人均限额、消费看板）。工作量 XL，风险高——在 premise 2 未验证的情况下投入这个等于给未验证假设加杠杆。

### Approach C：部门消费周报（侧向）
在现有多杯合并下单基础上加一个免费小功能，纯观察型埋点，用于积累真实需求证据而不是继续在未验证前提上加码。工作量 S，风险低，但不直接产出可演示的商业化功能。

**这三个方案在会话中被提出后，用户没有选择其中任何一个，而是给出了更根本的修正**（见下方"Recommended Approach"）。

## Recommended Approach

**用户在讨论中修正了问题框架，最终收敛到的方案，比 A/B/C 任何一个都更清晰：**

**分发免费，商业化可选升级。**

1. **免费层（获客，验证阶段规格）**：企业自己（HR/老板）在飞书后台创建自建应用（跟当前 demo 完全一样的操作），把这个应用绑定**企业自己指定的瑞幸账号** token——注意这不是"某个员工的私人账号"，是企业专门为此准备的账号（哪怕现阶段就是老板自己的账号），这样才不会出现"员工用同事私人账号疯狂点单"的滥用风险。绑定动作由企业自己的技术/HR 人员照着一份操作文档完成，不是"零配置"，是"零开发成本"——这个区别要说清楚，避免误判为无脑即插即用。
2. **付费层（商业化）**：触发时机是免费层暴露出的具体摩擦——账号所有者离职导致 token 失效、或者企业主动要求对公结算而不是挂在个人账号名下。届时提供"企业套餐"：**MVP 阶段不追求自动化开票系统，先用最土的办法验证付费意愿**——HR 对公转账充值，bot 按券**核销**，消费记录人工月结对账。这里要拆成两个能力分别标注验证状态：
   - **"核销优惠券"——已验证**：`previewOrder` 会返回账号已有的 `couponCodeList`，`createOrder` 能把它用在下单上，这条链路本次会话已经实测跑通（参见 `产品开发/瑞幸Agent摸底/capability-matrix.md` 第 21/45 行）。
   - **"生成/铸造任意面值的自定义企业券"——未验证**：目前实测过的 MCP 工具里没有一个"创建新优惠券"的接口，`couponCodeList` 只是账号已经拥有的券。企业套餐要落地，大概率要依赖瑞幸商家后台的营销发券功能（如果账号有商家权限），这是一个**没有查证过的外部依赖**，不是复用现成能力。这一点在真正投入付费层开发前必须先确认。

选择这个方向的理由：它直接对应 premise 3（to B 获客）和 premise 1（企业福利差异化），同时避开了 Approach B 的"未验证先重投入"风险——免费层本身就是低成本获客，验证成本几乎为零；付费层用人工流程代替自动化系统，把"值不值得投入自动化"这个问题推迟到有真实付费信号之后再回答。

## Open Questions

- premise 2（多杯合并下单需求真实性）仍未验证，需要靠免费层实际使用数据反过来验证，而不是继续假设。
- 账号所有者离职/token 失效的运营风险，目前只有"企业自己换绑"这个人工兜底方案，没有自动化方案——这是刻意接受的验证阶段风险，不是被忽略的问题。
- 免费层没有用量上限机制：如果员工可以无限制刷企业账号点单，存在成本失控风险。验证阶段建议先靠"企业信任 + 事后可查的消费记录（已有 `tastes.js`）"这种软约束，不做强制额度限制，但这是一个需要在真实使用中观察的开放风险，不是已解决问题。
- A 类企业（已有免费咖啡）和 B 类企业（无内部供给）需要不同的产品功能优先级，本次会话未深入到具体功能拆分层面。
- 飞书 ISV 审核规范对"主动推送营销内容"的具体限制尺度，本次只做了合理推断（企业对广告骚扰零容忍、管理员可一键移除），没有查证飞书官方审核细则文本。
- "生成/铸造自定义企业优惠券"这个能力没有查证过是否存在（瑞幸商家后台是否支持），必须在投入付费层开发前先确认，否则整个付费层的技术前提可能不成立。
- 验证阶段（自建应用+单租户）跑通后，如果要迁移到规模化阶段（ISV 应用商店多租户），已绑定的 token、已发放的优惠券、已积累的消费记录（`tastes.js`）怎么平滑迁移，本次会话没有讨论，是后续需要单独设计的问题。
- 付费转化触发点目前只设计了两个被动/事故型场景（token 失效、企业主动要求对公结算），没有设计主动的商业化触发机制（比如用量达到某个阈值时主动推荐套餐）——这是刻意选择的保守设计，不是遗漏。

## Success Criteria

本次会话产出的是方向判断，不是可量化的技术验收标准。真正的成功标准应该是下一步的验证目标：至少找到 1 个真实企业（哪怕是团队内部或身边公司）愿意在飞书里添加这个免费 bot 并产生至少一次真实下单，以此替代"访谈里提到过"这种软证据。

## Dependencies

- 依赖已完成的技术地基：`产品开发/飞书机器人-LuckyBarista/`（订单模式、DIY 收集模式、多杯合并、防幻觉商品校验、支付二维码、口味历史记录 `tastes.js`）。
- 依赖真实的用户访谈材料库（`用户访谈/`）作为后续验证的对照基准，避免重复本次会话里"把团队推断当成访谈事实"的错误。

## The Assignment

去找 1-2 个真实的、具体的职场人（不是"上班族"这个类别，是一个能叫出名字的人），直接问一句话："如果你们公司飞书里能加一个瑞幸机器人，@ 一下就能下单，你会加吗？在什么情况下你会想起来用它？" 把回答原话记下来，不要转述成"用户觉得很方便"这种概括。这是把 premise 2 从推断变成证据的最快方式，比继续设计功能更重要。

## What I noticed about how you think

- 我提出"老板买单是团队推断还是访谈原话"这个问题时，你没有为自己辩护，直接承认"是推断"——这个诚实度在头脑风暴里很少见，大多数人会找理由证明自己是对的。
- 你纠正了我"飞书能无限制推送营销消息"这个错误判断，而且给出的理由是具体的（企业对广告骚扰容忍度低、管理员会移除应用），不是单纯反对——这是有理由的纠正，不是情绪化的反驳。
