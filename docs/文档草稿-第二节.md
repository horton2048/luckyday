# 2. 方案优势/创新点

**核心突破点**：这个"数字员工"由商家（瑞幸）自己创建、自己拥有，不是被动等第三方 AI 平台调用。瑞幸官方已经有 MCP + CLI，能在电脑上用命令行完成下单，但 CLI 对绝大多数普通用户（尤其是老板/HR 这类非技术人员）完全不可用。我们把这个锁在开发者工具里的能力，原样搬进飞书——企业员工真正每天在用的工作界面，变成一个真正能用的数字员工。更关键的是所有权：AI 员工最核心的资产是用户交互数据、会话历史、偏好画像，这些只有在"商家自己拥有并运营这个 Agent"的架构下才留得住——不是被动等着被调用，是主动把执行入口开在企业最高频的工作场景里，自己攥住调用权。这正是对命题"推荐权、调用权、执行权"最直接的回应。

**AI 能力创新用法**：
- 双模式路由——一次轻量分类调用判断"直接下单"还是"DIY 收集"，两套系统提示词互不干扰，不用一个又长又啰嗦的提示词硬撑所有场景
- "本地伪工具"设计——DIY 收集收敛时，让模型用结构化参数（`resolveDiy`）报告结果，而不是把内部状态（"研发进度 3/5"这种）暴露给用户，用户只看到干净的对话
- 防幻觉护栏——开发过程中真实抓到过大模型会凭训练记忆"编"出恰好合法的商品 ID 去下单，我们加了一层代码校验：`previewOrder`/`createOrder` 里的每个商品，必须能在本次会话真实工具调用结果里追溯到，查不到就拦截，不放行

**预计可产生的量化价值估算**（估算，非实测数据）：4-6 人小会点单场景，人工逐一确认口味、逐一下单，估算单次操作 5-10 分钟，还容易漏单/记错口味；用这套方案，群里一句话收集偏好、自动合并下单，估算 1-2 分钟完成，并有防幻觉校验兜底不会下错商品。

## Before / After

| | Before（现状） | After（用了这套方案） |
|---|---|---|
| 团队/会议点单 | 老板/HR 逐一打开小程序，逐人配置口味，或在群里接龙、垫钱报销 | 群里一句话收集多人偏好，自动合并成一单，一次支付 |
| 钱与工作场景 | 员工垫钱→事后报销，或老板转账→员工自己下单，"钱"这一步永远要跳出飞书 | 提出需求→下单→支付全程不离开飞书，费用直接挂在企业账号 |
| 预定/周期性下单 | 官方小程序不支持提前预定（已实测验证），只能即时下单，团队咖啡永远要靠人当天手动发起 | Agent 层支持定时任务触发批量下单，一次设置、长期生效 |
| Agent 生态位置 | 瑞幸依赖 App/小程序等自有渠道触达用户，CLI/MCP 能力锁在开发者工具里，普通用户碰不到 | 瑞幸以"商家自建数字员工"的身份主动进驻企业最高频的工作场景，掌握用户交互数据和调用权，不是被动等第三方 Agent 调用 |
